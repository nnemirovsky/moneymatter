# Web Push notifications

## Overview

Every in-app notification (the bell) can also reach the user's devices as a browser Web Push notification, including when the tab, the window or the whole browser is closed (Safari on macOS delivers with Safari quit). The first reason is subscription payment reminders ("Payment reminder: Apple Music"), but the hook sits under every notification type, so tag reminders, bank-sync confirmations, sharing and household events and release notes can push too.

The plan delivers:

1. **Instance configuration:** VAPID keys through `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`. With any of them unset or invalid the feature is off: nothing is queued and the Notifications settings tab is hidden. One documented command generates the keys.
2. **Device subscriptions:** a `PushSubscriptions` table (one row per browser profile, unique by endpoint) and endpoints to read the config, subscribe, re-sync on app load, list devices, remove a device, unsubscribe the current device, and send a test notification.
3. **Delivery:** one fan-out hook in `createNotification` (and the release-notification bulk insert) queues a BullMQ job after commit. Its worker sends one standards-based push per device with the `web-push` library, honours per-group preferences, removes dead subscriptions (404/410) and retries transient failures per device.
4. **Service worker:** a small first-party worker at `/sw.js` (built from TypeScript) that always shows a notification for a push, opens or focuses the app on click, marks the notification read through the app, and re-subscribes on `pushsubscriptionchange`. Payloads use the Declarative Web Push JSON shape with `mutable: true`, so Safari 18.4+ still runs the worker's `push` handler (read state, badge, routing) and can show the declarative notification itself if the worker fails.
5. **Settings → Notifications:** "Browser notifications on this device" with every permission state (unsupported, iOS outside the Home Screen app, default, denied, enabled), per-group switches, the device list with remove, and a test button.
6. **Docs:** a user page and the self-host environment reference.

Out of scope: email preferences, localizing the stored English notification titles (the push title is the bell's title), native app push (APNs/FCM SDKs), and any new notification types.

The work happens in the fork on `feat/web-push` (cut from `dev`) and is offered upstream, so nothing is owner-specific and it works on hosted and self-hosted instances alike.

- **Browser facts (verified 2026-10-17):**
  - Safari 16+ on macOS 13 Ventura supports standard Web Push (VAPID, no Apple Developer account). A `webpushd` daemon receives pushes and wakes Safari, so delivery works with no tab open and **Safari not running**. A subscription must use `userVisibleOnly: true`, every push must show a notification through the Notifications API, and "violations of the `userVisibleOnly` promise will result in a push subscription being revoked". Requesting a subscription needs an explicit user gesture. Endpoints are on `*.push.apple.com`. ([WebKit: Meet Web Push](https://webkit.org/blog/12945/meet-web-push/))
  - iOS/iPadOS 16.4+ supports it only for a web app added to the Home Screen, whose manifest `display` is `standalone` or `fullscreen`; the permission request must come from a direct user action (a tap). The Badging API (`setAppBadge`) works in the foreground and while handling a push. ([WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/))
  - **Declarative Web Push** (Safari 18.4 on iOS/iPadOS, macOS 15.5): a JSON payload with top-level `"web_push": 8030` and a `notification` object (`title` required, `navigate` required, plus `body`, `lang`, `dir`, `silent`, …) is shown by the browser itself. Browsers without support hand the same JSON to the worker. ([WebKit: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/), [Safari 18.4 features](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)). Where `app_badge` belongs is unsettled ([WebKit bug 296773](https://bugs.webkit.org/show_bug.cgi?id=296773)), so this plan does not send it.
  - **The worker's `push` event fires for a declarative message only when the payload carries a top-level `"mutable": true`.** `mutable` defaults to false; the Push API parser starts with "Let mutable be false" and reads `message["mutable"]` when it is a boolean, and the receive steps dispatch `push` only "if declarativeResult's mutable is true and registration is non-null"; otherwise the user agent shows the notification itself and the worker never runs. WebKit mirrors this: `NotificationPayload` has `bool isMutable { false }` (`Source/WebCore/Modules/notifications/NotificationPayload.h`, persisted by `NotificationPayloadCocoa.mm`). With `mutable: true` and an installed worker, the worker's own notification replaces the proposed one; if the worker fails to show one, the declarative one is shown. ([Push API: declarative push messages](https://w3c.github.io/push-api/), [WebKit `NotificationPayload.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/notifications/NotificationPayload.h)). Browsers without declarative support ignore the unknown key.
  - **A mutable declarative `push` event has no `data`.** The receive steps fire it "given registration, null, and a new Notification object representing notification", so `event.data` is `null` and `event.notification` is the parsed notification, whose `data` member is the payload's `notification.data`. WebKit builds it the same way: `PushEvent::create(type, initializer, proposedNotification, proposedAppBadge, …)` passes `std::nullopt` for the data, and `PushEvent.idl` exposes `notification` (and `appBadge`) next to `data`. Browsers without declarative support still deliver the JSON in `event.data` with `notification` undefined. The worker therefore has to read `event.notification` first and `event.data` second. ([Push API: receiving a push message](https://w3c.github.io/push-api/#receiving-a-push-message), [WebKit `PushEvent.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/push-api/PushEvent.cpp), [`PushEvent.idl`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/push-api/PushEvent.idl)).
  - Apple's push service answers **403 `BadJwtToken`** when the VAPID `sub` claim is not a valid `mailto:` or `https:` URL; a `mailto:` address on `localhost`/`.local` is a known trigger. ([Apple: Sending web push notifications](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Apple Developer Forums](https://developer.apple.com/forums/thread/725473), [yuvomi release note](https://newreleases.io/project/github/ulsklyc/yuvomi/release/v1.66.2))
  - `web-push` 3.6.7 (latest, Node ≥ 16, depends on `http_ece` 1.2.0): `sendNotification(subscription, payload, { TTL, urgency, topic, timeout, vapidDetails })`; TTL defaults to 4 weeks; urgency `very-low|low|normal|high`; topic ≤ 32 URL-safe base64 characters, used by the push service to coalesce messages; `generate-vapid-keys --json` CLI. ([web-push README](https://github.com/web-push-libs/web-push))
  - Payload limit: RFC 8291 caps the encrypted record at 4096 bytes, which leaves 3993 bytes of plaintext with `aes128gcm` (4096 − 86 header − 16 tag − 1 padding delimiter).
  - A `<link rel="manifest">` is fetched **without cookies** unless it carries `crossorigin="use-credentials"`, even same-origin, so behind an authenticating proxy the manifest request is redirected to the login page. ([MDN crossorigin](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/crossorigin), [GitLab issue 457527](https://gitlab.com/gitlab-org/gitlab/-/issues/457527))
- **Instances behind an auth proxy (Cloudflare Access and similar):** delivery is backend → push service (Apple, Google, Mozilla, Microsoft) → browser, so the proxy is never on the delivery path. The browser fetches `/sw.js` and its updates same-origin with the proxy cookie; if that session has expired, an update fetch is redirected and fails, the installed worker keeps running, and delivery is unaffected. The manifest needs `crossorigin="use-credentials"` (above). The worker's own `pushsubscriptionchange` re-subscribe request goes to the API with `credentials: 'include'`, which carries the proxy cookie too.
- **Conventions (repo CLAUDE.md):** route → controller → service; object params and kebab-case files; e2e only through HTTP helpers, colocated with services, happy/empty/error per endpoint, run by the `test-runner` subagent and never in parallel; i18n keys for thrown errors; `en` + `uk` through `i18n-editor`; amend an unmerged migration instead of adding one; comments describe the current code; stop and ask after 1–2 failed fix attempts.

## Decisions (after reading the code)

- **One fan-out hook, at the insert.** `createNotification` calls `enqueueWebPushAfterCommit({ notificationIds: [row.id] })` right after `Notifications.create`; `createReleaseNotifications` does the same with the ids `bulkCreate` returns. No caller changes, so every current and future type pushes. The helper is a no-op when VAPID is not configured, defers to `afterCommit` when a transaction is active (the logo-queue pattern), and never throws into or blocks the write path:
  - **fire-and-forget:** the `afterCommit` callback detaches the enqueue (`transaction.afterCommit(() => { void enqueue(…) })`) and returns at once; the same call without a transaction is also `void`;
  - the detached `enqueue` races `queue.add`/`addBulk` against a 2 s timeout and logs a warning (`[Web Push] enqueue failed or timed out`, no payload) on either failure; a notification written while Redis is down simply gets no push, as the bell entry is the source of truth;
  - the producer `Queue` gets its own connection options with `enableOfflineQueue: false`, so `add` fails fast instead of piling commands in ioredis's offline queue (the `Worker` keeps the blocking `maxRetriesPerRequest: null` connection).
- **The push shows what the bell shows, rendered by a backend mirror of the bell.**
  - **Title** = the stored `title` (`changelog`: the backend-built "New version {version}" in the user's locale, as the bell builds it client-side). Localizing the English titles that sharing and subscription reminders store is a separate change for bell and push alike.
  - **Body** comes from `renderPushBody({ notification, locale })`, which follows `notification-item.vue` per type:
    - `changelog`: the release name (`ChangelogContent`).
    - `tag_reminder`: `<tagName> · <message>`. The bell builds the message client-side from the payload (`TagReminderContent`), not from the stored `message`: the threshold text with the actual and threshold amounts formatted in the payload's currency, or the existence text with the transaction count. The renderer uses `Intl.NumberFormat` with the user's locale and the payload `currencyCode` (`USD` when absent, as the bell does; the plain number plus the code when `Intl` rejects a custom code).
    - the 18 share and household types in `SHARE_NOTIFICATION_TYPES` (every `share_*` and `household_*` type except `share_owner_budget_deleted`). The list moves out of `notification-item.vue`, where it is a local constant, into `packages/shared/src/types/notifications.ts` as an exported constant that the bell and `render-push-body.ts` both import: `@<counterpart> · <resourceName>`, where the counterpart is `owner.username` for the received invitations, `inviteeSnapshot.username` or else `inviteeEmail` for the send-failed ones, and `counterpartUser.username` for the rest; the two send-failed types add a second line with the send-failed hint. Parts that are missing are left out, and with neither part there is no body (the bell shows nothing then either).
    - every other type, `share_owner_budget_deleted` included (the bell falls through to `DefaultContent` for it): the stored `message`, else no body.
  - **Why a backend renderer, not a shared formatter:** the bell's strings live in the frontend i18n files and its amounts go through frontend formatters, so a formatter in `packages/shared` would have to carry the i18n and currency formatting along. The backend already has i18next with `en` and `uk` and the user's `settings.locale`. The cost is three strings mirrored from the bell's keys (`notifications.tagReminder.thresholdMessage`, `notifications.tagReminder.existenceMessage`, `notifications.share.sendFailedHint`), added as `webPush.body.*` with the same wording (the `i18n-editor` copies it from those keys), so the unit tests per group are what keep the two in step.
- **Click target: the app decides, the backend does not duplicate routes.** The push carries `data.path = /notifications/<id>` (a new frontend route). The route page loads the notification by id, marks it read and replaces itself with `buildNotificationRoute(notification)` (or the dashboard with the bell open when the type has no target). The bell click (which already holds the notification) and a click relayed from the worker (which has only the id) go through the same `useOpenNotification` composable. No per-type URL logic on the backend.
  - **A missing notification is a 200 with a null body, not a 404.** `GET /api/v1/notifications/:id` returns `{ status: 'success', response: null }` when no row matches `{ id, userId }`: `getNotificationById` in `services/notifications/index.ts` yields `null`, the controller returns `{ data: null }`, and `notifications.e2e.ts` already asserts `toBeNull()` for an unknown id. That covers an id that never existed, a notification wiped by a data wipe or backup restore, a deleted account, and another account's notification on a shared browser. The plan keeps this contract and does not add a 404. The new frontend `getNotificationById` returns `NotificationStruct | null`, and `useOpenNotification` treats `null` as missing (toast, then the dashboard).
- **Per-group preferences in user settings, not per type.** 26 types are too many switches. `notifications.push.groups` gets five optional booleans; the type→group map lives in `shared` as a `Record<NotificationType, PushGroup>`, so a new type does not compile until it is placed:
  - `reminders`: `subscription_reminder`, `tag_reminder`, `budget_alert` (default on);
  - `bankSync`: `planned_confirmed`, `stuck_pending` (default on);
  - `sharing`: every `share_*` and `household_*` type (default on);
  - `system`: `system` (default on);
  - `releases`: `changelog` (default **off**: it fans out to every active user per release).
  - The dormant `notifications.enabled`/`types` keys stay, but both become optional in `ZodNotificationPreferencesSchema` (no `.default()`): the PATCH path re-validates the merged settings with the full schema, which requires `types` today, so saving a group on any existing row would answer 422 (see Context). Nothing reads either key (see open questions).
  - The groups are per user, not per device: one place to set them, and a device is either on or off.
- **Delivery: two BullMQ job kinds on one `web-push` queue.**
  - `fan-out` (`jobId` `push-fanout-<notificationId>`): load the notification; skip unless it is still `unread` and not expired, its group is enabled and the user has subscriptions; then add one `deliver` job per subscription.
  - `deliver` (`jobId` `push-<notificationId>-<subscriptionId>`, 5 attempts, exponential backoff from 30 s): re-check the notification is still unread (a user who read it in the app meanwhile gets no stale push), **load the subscription by `id` and the notification's `userId` together and skip when no row matches** (Enable moves a row to another account under the same id, so a browser handed over while a push waits or backs off must not receive the previous account's text), build the payload, send.
  - One job per device means a retry never re-sends to a device that already got it.
  - **Every query on the worker path passes `transaction: null`** (notification load, unread count, subscription reads, updates and deletes), and so does `sendToSubscription`'s bookkeeping, like `resolveBrandLogo`. The worker shares a process with the HTTP server, and cls-hooked can bleed a concurrent request's already-committed transaction into an unpinned query ("commit has been called on this transaction"), which would fail the job and re-send pushes on retry. An explicit `null` skips the CLS lookup. Only `enqueueWebPushAfterCommit` reads the CLS transaction, on purpose, and only to defer.
- **Result handling.** `sendToSubscription` first checks the endpoint allowlist and the key, then sends, then classifies the response into `ok` | `gone` | `rejected` | `instance` | `retry`:
  - **Key change, before any request:** a subscription whose `vapidKeyId` differs from the current key is deleted without sending (the push service would answer 403 for it). This is the only key-change mechanism, and it lives in `sendToSubscription`, so the test push gets it too.
  - 201/202 (`ok`): `lastSuccessAt = now`, `failureCount = 0`.
  - 404 or 410 (`gone`): delete the subscription (the browser dropped it).
  - 400 (`rejected`, a fault of the subscription itself): no retry (`UnrecoverableError`), `failureCount += 1`, `lastFailureAt`, `lastFailureStatus`. A stored endpoint that the allowlist now refuses is `rejected` too. A subscription with 10 consecutive `rejected` results is deleted.
  - 401, 403 or 413 (`instance`: the push service refused this instance's VAPID JWT, for example a bad key, clock skew or an `ExpiredJwtToken`, or the payload was too large): no retry, `lastFailureAt` and `lastFailureStatus` recorded, **`failureCount` untouched and never a deletion**. One misconfigured instance must not delete every user's devices. It is logged once per process per endpoint host and status (a module-level set), and reported to Sentry once.
  - 429, 5xx, timeouts and network errors (`retry`): throw, so BullMQ retries. When the attempts run out, only `lastFailureAt` and `lastFailureStatus` are recorded; `failureCount` is untouched.
  - Only `rejected` results count toward the prune, and any `ok` resets the count.
- **TTL, urgency, topic:** TTL 24 h for notifications, 120 s for the test push; urgency `normal`, `high` for the test; topic = the notification id without hyphens (32 hex characters, valid), so the push service coalesces a retry with its pending original.
- **Payload: Declarative Web Push JSON, read by our worker.** `{ web_push: 8030, mutable: true, notification: { title, body?, navigate, lang, tag, silent: false, data: { v: 1, kind, notificationId?, type?, path, unreadCount } } }`, where `navigate` = `FRONTEND_BASE_URL + path`. `FRONTEND_BASE_URL` is the cleaned value in `packages/backend/src/config.ts` (exported for this), so an `AUTH_ORIGIN` ending in `/` never yields `//notifications/<id>`.
  - `mutable: true` makes Safari 18.4+ fire the worker's `push` event (see Browser facts), which the badge update, the worker's icon and the click relay depend on. Without it Safari shows the declarative notification and skips the worker.
  - The declarative fields stay complete (`title`, `navigate`, `body`, `lang`, `tag`, `data`), so if the worker throws or is missing, Safari still shows a correct notification that opens `navigate`.
  - Other browsers hand the JSON to the worker, which uses the same fields. Title ≤ 200 characters (the column), body ≤ 500, and the serialized payload ≤ 3000 bytes (under the 3993-byte limit with headroom), trimming the body by code points with an ellipsis until it fits.
- **Endpoint allowlist against SSRF.** The backend POSTs to whatever endpoint a client registers, so a subscription endpoint must be `https:`, have no credentials, a non-IP hostname and a host matching the push services: `*.push.apple.com`, `fcm.googleapis.com`, `*.push.services.mozilla.com`, `*.notify.windows.com`. `WEB_PUSH_ALLOWED_HOSTS` (comma-separated, `*.` wildcards) replaces the list for self-hosters on another push service. Checked at subscribe (422) and again before every send.
- **VAPID config: backend env, exposed by an API endpoint, not `window.__APP_CONFIG__`.**
  - `GET /api/v1/push/config` returns `{ enabled, vapidPublicKey }`.
  - The private key and the public key must match, and only the backend has the private key. A copy of the public key in the frontend container's env could drift from the backend's after a key change (split-domain deployments set the two containers separately), and every subscription made with the stale key would then fail with 403.
  - The backend also decides whether the feature is on at all.
  - It costs one cached query on the settings page and on app load.
- **Validation of the keys at startup:** `getWebPushConfig()` returns `null` (feature off, one warning log) unless all three are configured (`isEnvConfigured`), the public key decodes to a 65-byte uncompressed P-256 point, the private key to 32 bytes, and the subject is `mailto:` or `https:` and not on `localhost`/`.local` (Apple's `BadJwtToken`). `vapidKeyId` = the first 16 hex characters of SHA-256 over the public key, stored on each subscription to detect a key change.
  - **Warnings never contain a value.** `warnOnce` in `common/utils/env.ts` (reached through `isEnvConfigured`) logs `${name}="${value}"` verbatim, so a `your-…` placeholder or any future rule failure would print the raw variable. To keep key material out of the logs, `warnOnce` prints `<redacted>` instead of the value for `VAPID_PRIVATE_KEY` and `VAPID_PUBLIC_KEY` (a small `REDACTED_VARS` set in `env.ts`). The checks that `getWebPushConfig` adds itself (decode, length, subject) name the variable and the reason only (`VAPID_PRIVATE_KEY must decode to 32 bytes`), never the value or its length.
  - The warning is logged once per process, keyed by variable and reason, because `getWebPushConfig` runs on every enqueue.
- **Subscriptions are explicit, per user, per browser profile.**
  - The endpoint is unique. **Enable** (`POST /subscriptions` without `oldEndpoint`, from a user's tap) is an upsert by endpoint that moves the row to the caller (holding the endpoint proves possession of that browser), so a browser handed to another account never pushes to both.
  - **Rotate** (`POST /subscriptions` with `oldEndpoint`, sent without a tap by the worker's `pushsubscriptionchange` and by the app-load reconcile) never enrols anyone. The exact rule, in one transaction:
    1. Look up the row with `endpoint = oldEndpoint` and `userId = caller`.
    2. **Found:** if the new endpoint already exists on another row, owned by the caller, that row is deleted and the old row takes its place; owned by another user, the request is refused with 409 and nothing changes (taking an endpoint over is reserved for Enable). Otherwise the old row is updated in place: same `id`, `userId` and `createdAt`, with the new `endpoint`, keys, `expirationTime`, `deviceLabel` and `vapidKeyId`, `failureCount = 0`. Answer 200 with the device.
    3. **Not found, but the caller already owns a row with `endpoint = new endpoint`:** the rotation already happened (the worker's `pushsubscriptionchange` request ran first, so the page's stored endpoint is stale). This is an idempotent success: refresh that row's keys, label and `lastSeenAt`, create and move nothing, answer 200 with the device. The app reads the 200 as `known: true`, stores the new endpoint and keeps the subscription.
    4. **Otherwise:** 404 `webPush.subscriptionNotFound`, nothing written. A device removed from another device's list or deleted by `sync` has no row under either endpoint, so it stays removed; another user's `oldEndpoint`, or a new endpoint owned by another user while the old row is gone, also ends here.
       Step 3 touches only a row the caller already owns, so it enrols no device and no account. Pending `deliver` jobs keep working because the row id never changes.
  - `sync` (called on app load when the browser has a subscription and no rotation applies) only refreshes the caller's own row. If the endpoint belongs to another user it deletes that row, and it never inserts, so a user who never opted in on a shared browser never gets subscribed silently. On `known: false` the app also unsubscribes the browser subscription and clears the stored endpoint, so a browser whose device was removed elsewhere cannot come back through a later rotation either.
  - **The app remembers the endpoint it registered.** Enable and a successful Rotate (200) store the endpoint in `localStorage` under a per-user key. A service worker cannot write `localStorage`, so after its own successful Rotate it posts `{ type: 'push-endpoint-changed', endpoint }` to every open same-origin window and the dashboard's message listener stores it; when no window is open, the idempotent step 3 above covers the next load. `syncOnLoad` compares it with `pushManager.getSubscription()`: when they differ the browser rotated without the worker's event arriving, and the app sends Rotate with `{ ...subscription.toJSON(), oldEndpoint: <stored> }`. Disable, an explicit logout and a `known: false` answer clear it; an expired-session logout keeps it. Without a stored value (cleared storage), `syncOnLoad` falls back to `sync`, so the toggle shows off and nothing is re-enrolled; the user taps Enable.
  - **Only an explicit sign-out unsubscribes the device.** `logout({ demoEndReason, disablePush })` takes `disablePush` (default `false`). `useLogout` (`composable/actions/logout.ts`, the user menu) and the account-deletion flow pass `true`: the server row and the browser subscription go first, best-effort, before `signOut`. The automatic path is untouched: `api/_api.ts` calls `useAuthStore().logout()` on every `unauthorized` response (sessions last 7 days), and `demo-banner.vue` logs out on expiry, so neither passes the flag. An expired session therefore keeps the subscription and the row, push keeps arriving, and the next sign-in finds `known: true`. The `/unsubscribe` call of an explicit logout is sent with a plain `fetch` in `api/web-push.ts` (`credentials: 'include'`, errors ignored), not through `_api.ts`, so a 401 cannot re-enter `logout()` and loop (the hazard the comment in `_api.ts` describes).
- **Service worker: a first-party worker, not `vite-plugin-pwa`.**
  - The app needs no offline cache, and a Workbox precache would fight the existing `version.json` reload prompt.
  - The worker has no `fetch` handler, so it never sits on the request path. It is about 100 lines.
  - Source in `src/service-worker/` (TypeScript, `WebWorker` lib). The logic lives in pure modules that vitest covers.
  - A small Vite plugin bundles it with esbuild into a classic script, emitted as `/sw.js` at build time and served by middleware in dev.
  - The dead `registerServiceWorker.ts` and the `register-service-worker` dependency go.
- **Registration timing:** the worker is registered when the Notifications settings page mounts (on a supported browser with push enabled on the server) and on app load when a registration already exists. The subscribe click then calls `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` as its first `await`, which raises the permission prompt inside the gesture. Registering inside the click and awaiting `serviceWorker.ready` first would lose Safari's gesture.
- **A stale-key subscription is removed outside the click.** Subscribing with a different `applicationServerKey` while a subscription exists throws `InvalidStateError`, and unsubscribing first would put an `await` before `subscribe`. So the reconcile step compares the browser subscription's `options.applicationServerKey` with the config key on app load (`syncOnLoad`) and when the settings page mounts, once the config has loaded: on a mismatch it unsubscribes in the browser, calls `/unsubscribe` (best-effort) and leaves the toggle off. `enable()` stays `subscribe` first. As a safety net, if `subscribe` still throws `InvalidStateError` (the reconcile had not run yet), `enable()` removes the stale subscription _after_ that failed call and asks the user to tap again; a second tap has its own gesture.
- **The worker always shows a notification** for every push, including when the payload is unreadable (a generic "MoneyMatter" / "You have a new notification") and when an app window is focused. Safari revokes subscriptions that skip it.
- **The `push` handler reads both event shapes.** `parsePushEvent({ notification, dataText })` takes `event.notification` first (Safari 18.4+, mutable declarative message, `event.data` null): title, body, tag, lang and `data` come from that object, so the path, notification id and unread count survive. Without `event.notification` it parses `event.data.text()` as JSON (every other browser, and the classic Safari path), and only when both are missing or unusable does it show the generic fallback. A declarative event must never fall into the generic fallback.
- **`notificationclick`:** if a same-origin window exists, focus it and send `{ type: 'notification-click', notificationId, path }` through a `MessageChannel`; the app routes in place through `useOpenNotification` and answers on the channel port. The worker waits up to 1 s for that acknowledgement. Without one (the window shows the sign-in page, whose layout `layouts/auth.vue` has no receiver, or is still loading), it calls `client.navigate(origin + path)` on that window, and the route guard then keeps the destination as `redirect: to.fullPath` through sign-in (`routes/guards.ts`). With no same-origin window it calls `clients.openWindow(path)`. Marking read happens in the app with its session, so the worker makes no authenticated call here.
- **`pushsubscriptionchange`:** subscribe again with the old options and send Rotate: POST `{ ...newSubscription.toJSON(), oldEndpoint: event.oldSubscription.endpoint }` to the API (base URL passed as `?api=` on the worker's script URL, `credentials: 'include'`). `PushSubscription` exposes `endpoint` and `expirationTime` as prototype getters and the keys through `getKey()`/`toJSON()`, so a spread of the object itself would send nothing; `toJSON()` is required. Without `event.oldSubscription` the worker sends nothing. The app-load reconcile (stored endpoint, see Subscriptions) is the fallback, since Safari may not fire the event and the request fails on an expired session.
- **Backups: exclude `PushSubscriptions`.** Rows are bound to one browser profile and to this instance's VAPID key; restored onto another instance or after a key change they would push to dead or foreign devices. The group preferences live in user settings and are backed up with them.
- **Guard and plan coverage:**
  - Every push write is exempt from `checkBaseCurrencyLock` (device registration, no monetary data; turning notifications on or off must work during a base-currency change).
  - `/push/` joins `READ_ONLY_PREFIXES`, so a read-only plan keeps its reminders.
  - Subscribe and test are `blockDemoUsers`.
  - Subscribe/sync/unsubscribe/delete are limited to 30 per minute per user, the test push to 5 per minute.
- **Feature off:** `GET /push/config` → `{ enabled: false, vapidPublicKey: null }`; subscribe, sync and test → 404 `webPush.notConfigured`; list, delete and unsubscribe keep working so old rows can be cleaned up. The settings tab is hidden.
- **Tests mock the push service over HTTP (MSW), not the `web-push` module.**
  - MSW is the repo's pattern for outbound HTTP. The real library then signs the VAPID JWT and encrypts with `aes128gcm` in every test.
  - The test owns the subscription's private key, so it decrypts the captured body (`http_ece`, dev dependency) and asserts the exact payload.
  - Mocking the module would test none of the wire format.
  - Retry delays come from one constant, 30 s in production and 0 under `NODE_ENV=test` (a failed attempt returns to the waiting list at once, which the retry-ordering e2e needs; see Technical Details → Worker), and the worker's concurrency is 1 under `NODE_ENV=test`, so jobs that do not retry finish in the order they were queued and a retry lands before any job queued after its failure.
  - **"No push" cases assert positively.** Absence after a wait proves nothing when a job can still be pending. Each such case ends with a _sentinel_: a notification in an enabled group, created over HTTP after the one that must not push. The test waits for the sentinel's request (with concurrency 1 its fan-out job runs after the earlier single-attempt job has finished, so that job has already decided; a case with a retry uses the ordering described under "already read") and then asserts that the captured requests are exactly the sentinel's.
- **Badge:** the worker calls `navigator.setAppBadge(unreadCount)` when supported (Home Screen apps, installed desktop apps), and the app syncs the badge with the polled unread count and clears it at zero.
- **Manifest hardening:** `crossorigin="use-credentials"` on the manifest link (auth proxies), and `"id": "/dashboard"`, which equals the id browsers derive today from `start_url`, so existing installs keep their identity.

## Technical Details

- **Env (backend):**
  - `VAPID_PUBLIC_KEY`: base64url, 87 characters.
  - `VAPID_PRIVATE_KEY`: base64url, 43 characters.
  - `VAPID_SUBJECT`: `mailto:admin@example.com` or `https://example.com`.
  - `WEB_PUSH_ALLOWED_HOSTS`: optional.
  - Key generation for self-hosters: `docker compose exec backend npx --no-install web-push generate-vapid-keys --json` (the CLI ships with the dependency), or `npx web-push@3.6.7 generate-vapid-keys --json` on any machine with Node.
  - Changing the keys invalidates every existing subscription; users re-enable on each device.
- **`PushSubscriptions`:**
  - `id` (uuid);
  - `userId` (FK `Users`, cascade);
  - `endpoint` (text, unique);
  - `p256dh` (string 128) and `auth` (string 64), base64url;
  - `vapidKeyId` (string 16);
  - `expirationTime` (date, null);
  - `userAgent` (string 512, null);
  - `deviceLabel` (string 100, null);
  - `lastSeenAt`, `lastSuccessAt`, `lastFailureAt` (dates, null);
  - `failureCount` (int, default 0);
  - `lastFailureStatus` (int, null);
  - timestamps;
  - index `(userId)`.
  - Migration `migrations/20261017030000-create-push-subscriptions.ts`.
- **API** (session auth, all under `/api/v1/push`):
  - `GET /config` → `{ enabled: boolean, vapidPublicKey: string | null }`.
  - `POST /subscriptions`:
    - body `{ endpoint, keys: { p256dh, auth }, expirationTime?, deviceLabel?, oldEndpoint? }`;
    - without `oldEndpoint` (Enable): upsert by endpoint, moves ownership;
    - with `oldEndpoint` (Rotate): replaces the caller's own row in place and never inserts (Decisions → Subscriptions); an `oldEndpoint` that is gone but whose new endpoint the caller already owns is an idempotent 200; otherwise 404 when no such row of the caller's exists, and 409 when the old row exists and the new endpoint belongs to another user;
    - returns the device DTO; 201 when inserted, 200 when updated or rotated;
    - 422 for a disallowed endpoint or malformed keys (p256dh decodes to 65 bytes, auth to 16).
  - `POST /subscriptions/sync`: body `{ endpoint }` → `{ known: boolean }` (see Decisions).
  - `GET /subscriptions` → `[{ id, deviceLabel, endpointHost, endpointHash, createdAt, lastSeenAt, lastSuccessAt, lastFailureAt, failureCount }]`. `endpointHash` is the first 16 hex characters of SHA-256 over the endpoint, which lets the client mark "This device" without the server returning the capability URL.
  - `DELETE /subscriptions/:id`: 404 for another user's id.
  - `POST /subscriptions/unsubscribe`: body `{ endpoint }`, idempotent. A POST body keeps the endpoint out of URLs and access logs.
  - `POST /test`: no body; sends synchronously to all of the user's devices and returns `{ sent, failed, removed }`. (A per-device test would need a per-row button first; none is planned.)
- **Settings shape:** `notifications.push.groups.{ reminders, bankSync, sharing, system, releases }`, optional booleans in both `ZodSettingsSchema` and `ZodSettingsPatchSchema` (no `.default()`, as the PATCH deep-merge rule requires). Defaults are applied by `isPushGroupEnabled`. They are edited through the existing `PATCH /user/settings`. In `ZodNotificationPreferencesSchema`, `enabled` and `types` become `.optional()` without defaults, so `{ notifications: { push: { groups: { reminders: false } } } }` passes the full-schema re-validation for a row that has never stored them.
- **Payload example:**

  ```json
  {
    "web_push": 8030,
    "mutable": true,
    "notification": {
      "title": "Payment reminder: Apple Music",
      "body": "\"Apple Music\" is due on 2026-10-20",
      "navigate": "https://money.example.com/notifications/7c0e…",
      "lang": "en",
      "tag": "7c0e…",
      "silent": false,
      "data": {
        "v": 1,
        "kind": "notification",
        "notificationId": "7c0e…",
        "type": "subscription_reminder",
        "path": "/notifications/7c0e…",
        "unreadCount": 3
      }
    }
  }
  ```

  The test push uses `kind: "test"`, tag `push-test` and path `/settings/notifications`, and carries `mutable: true` as well.

- **Logging:** `[Web Push]` with the subscription id, endpoint host, status code and job id. Never the endpoint path, keys, JWT or payload. Unexpected errors go to Sentry, expected statuses do not. Instance-side statuses (401, 403, 413) are logged and reported once per endpoint host and status. Config warnings (see Validation of the keys) never contain a variable's value.
- **Worker:** concurrency 10 (1 under `NODE_ENV=test`), a 10 s request timeout, `removeOnComplete`, failed jobs kept for 1 h. Its retry backoff is 30 s in production and **0 under `NODE_ENV=test`**: BullMQ moves a failed attempt with a non-zero retry delay into the delayed set, but puts a zero-delay retry straight back on the wait list. The delivery e2e ("already read", "ownership moved") needs the retry to run before the sentinel's deliver job, and a delayed retry would let the sentinel arrive first and the guards go untested. A single constant feeds both Decisions and this line.
- **nginx:** `location = /sw.js { root /app; add_header Cache-Control "no-cache" always; add_header X-Content-Type-Options "nosniff" always; }`. The exact match outranks the immutable `\.js$` rule, like `/config.js`.
