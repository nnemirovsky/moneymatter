# AI chat: ask, attach, approve

## Overview

A chat inside MoneyMatter where the user types, attaches files and gives instructions. The AI reads the request and the attachments, looks at the user's data through the same tools the MCP server exposes, and answers in one of two ways:

- **Acting** ("log these receipts", "move all Bolt rides to Transport", "delete the duplicates from March"): no prose. Every change is a **card**, one per change, which the user approves, rejects, edits inline or comments on. Nothing changes until a card is approved. Approving runs the original MCP tool handler with the user's own auth context.
- **Answering** ("where did my money go in September?"): text plus charts, tables and KPI tiles, drawn by the frontend from a small, validated spec. Numbers come from the existing stats tools or from the AI's own JavaScript, run in an isolated sandbox.

It runs on the model connections the user already has (per-feature picker, new `chat` feature): API-key providers through the AI SDK's in-process tool calling, and the Claude Code / Codex subscription connections through a bridge that gives the CLI MoneyMatter's own MCP server with a short-lived, run-scoped token whose write tools only propose.

The plan is generic, because the branch is offered upstream (`letehaha/moneymatter`): `en` + `uk`, docs, hosted and self-hosted. It has three phases on one branch:

1. **Phase 1 (Tasks 1–18):** API-key providers, threads, attachments, cards, visuals, the Chat page and the slide-over panel.
2. **Phase 2 (Tasks 19–20):** the subscription CLI bridge.
3. **Phase 3 (Tasks 21–22):** sandboxed analytics.

Then Verify (Task 23) and Docs (Task 24). Every decision for all phases is in this one plan.

## Decisions

### Owner's decisions (binding)

1. **Providers:** reuse model connections and the per-feature picker with a new `chat` feature. API-key providers run in-process (AI SDK tool calling). Claude Code / Codex run through a bridge: the CLI gets only MoneyMatter's MCP server, with a short-lived chat-scoped token whose write tools propose instead of executing.
2. **One tool layer:** the MCP registry and handlers are the single source of capabilities, with the same guards. Reads run freely; every write becomes a proposal; approval runs the original handler with the user's own auth context.
3. **Cards:** one per change; approving a dependent card also applies its parents, with a note; destructive actions are allowed as red danger cards listing exactly what goes (counts + preview rows), with a typed or second confirmation for bulk ones; no undo; approve / reject / edit inline / comment; an expandable "details" with sources; no free-form text when acting.
4. **Uncertainty:** low → best guess with highlighted uncertain fields; high → a clarifying choice card first.
5. **Questions:** text plus charts from a small safe spec rendered with the repo's chart library (d3).
6. **Analytics:** every stats tool, plus JavaScript in an isolated sandbox.
7. **Attachments:** context only (images, PDFs, CSV, text), never saved onto transactions.
8. **UI:** a Chat page with history and search, and a panel from any page that knows the page context; container queries.
9. **History:** per user, never shared with household members, expires 30 days after the last message by default (7/30/90/365/never in Settings → AI), pinned threads never expire.
10. **Limits:** per-message step cap (25) and sandbox limits; token usage per thread; no money cap.
11. **Streaming** with cancellation and reconnect.
12. **Hosted model (answer to review question 1):** chat runs on the user's own connections only; whether hosted plans get an included model is upstream's call. The plan leaves a small, documented extension point for an operator-key model and adds no plan gating.
13. **Approve all (answer 2):** yes, one "Approve all safe" button per message, for safe cards only (defined under "Approve-all and safe cards"; red and egress cards are never safe).
14. **Applied-change records (answer 3):** they live and die with their thread (same retention), not 365 days.
15. **Unapproved cards (answer 4):** expire 24 hours after they were proposed, pinned threads included.

### Decisions (after reading the code)

- **The tool catalog comes from `server.ts` itself.** The body of `createMcpServer()` that registers tools moves into `registerAllTools(server: McpServer)` (same file, same group comments, same order; the 250 `registerX(server: McpServer)` signatures stay as they are). `createMcpServer()` calls it; `getToolCatalog()` (`services/mcp/tool-catalog.ts`) runs it once against a capture shim (cast `as unknown as McpServer`, as `captureTools` in `tests/helpers/mcp-tools.ts` does) and returns `{ name, description, inputShape, invoke, access, validateArgs }` for every tool. A new MCP tool therefore reaches the chat with no extra registration, and `server-registration-drift` keeps working (it reads `server.ts`).
  - **Both handler shapes:** `inputShape` is `null` for the 16 tools registered without an `inputSchema`, and `invoke({ args, extra })` calls `handler(extra)` for them and `handler(args, extra)` for the rest, so no call site deals with the arity. Their model-facing schema is an empty object. A drift case compares the `null`-shape set with a source scan for `async (extra) =>` in `tools/*.ts`, and a unit case invokes one tool of each shape.
  - **`validateArgs`:** every argument check the handler runs before its service call, other than the guards (scope, feature, lock, rate limit): shared schemas, `assert…Args` helpers, and refusal helpers such as `parseBulkTarget` and `hasNarrowingFilter` (`bulk_delete_transactions` refuses `filters: {}`, which would select every transaction the user owns). It comes from a registry `services/mcp/tool-arg-validators.ts` that maps tool name → validator. Task 2 moves each check into an exported `validate<Pascal>Args` in its tool file (or the shared schema it already uses), and the handler calls that function in place of the inline code.
    - **Drift:** the trigger is a handler body (the callback passed to `registerTool`, cut out of the source) containing `.parse(`, `.safeParse(`, `assert…Args(` or a name from a hand-kept `ARG_CHECK_HELPERS` list (`parseBulkTarget`, `hasNarrowingFilter`, `parseTransactionFilters`, …). Such a tool needs a registry entry, and the handler body itself (not just the file) must call the registered function, so a handler that stops calling its validator, or keeps an inline check beside it, fails the suite.
    - The chat runs `validateArgs` on proposal, on every edit, and at approval on the original args before any rewrite, so whatever the MCP tool refuses, the chat refuses too.
    - **Refs and validators, one helper:** `validateWithRefs({ entry, args })` (`services/chat/proposals/placeholders.ts`) validates a copy of the args in which every `$proposal:<id>` is replaced by a fixed placeholder UUID, a valid id of any kind, so `recordId()` and `z.uuid()` fields inside shared body schemas (`create_account_group.parentGroupId`, `create_holding.portfolioId`, `create_budget_plan_line.categoryIds`, `set_budget_plan_accounts.accountIds`, …) accept it, and runs the real schema plus `validateArgs` on that copy. It is used wherever parents may not exist yet: at proposal, on edit, in the AI SDK validate hook, and in approval check (c). Once a parent's handler has run inside the approval transaction, its real result id replaces the ref and the child's args are validated again with no placeholder left (approval step 3). The stored args keep their refs throughout.
  - The private `_registeredTools` is not read: it is SDK-internal and not in the jest mock.
  - `access` follows the name rule the scope drift test already enforces (`read` when the name matches `READ_TOOL_NAME`, else `write`). The classification constants move out of `tool-scopes-drift.unit.ts` into `services/mcp/tool-classification.ts`, and both drift suites and the chat import them.
- **Defence in depth on the read path:** a read runs with an `extra` whose scopes are only `['finance:read']` and `clientId: 'moneymatter-chat'`. If a write tool were ever misclassified as a read, its own `requireScope` would throw.
- **Proposals are made by a tool, not by AI SDK tool approvals.** Every write tool is exposed to the model with its own name and description and a **ref-tolerant** copy of its schema plus an optional `_chat` meta field (see "Model-facing schemas"). Its `execute` resolves `$proposal:` refs to placeholders, runs the tool's real schema and `validateArgs`, stores a `ChatProposals` row and returns `{ proposalId, ref: "$proposal:<id>", status: "proposed" }`. A validation failure is a tool error the model sees and can fix in the same run, so no card that would fail on its arguments is ever shown as approvable. `needsApproval` was considered and dropped:
  - it pauses the loop at the first write, while a statement import needs 40 cards from one turn;
  - its state lives in the message stream, while cards outlive the run (stale detection, edits, comments, approval days later);
  - the CLI bridge cannot use it.

  The same proposal tool runs in both paths, so cards are identical whatever the provider.

- **Card text is never model prose.** Titles come from i18n keys built from the tool's policy (`kind` + `entity`), field labels from a shared field-label map, and values from the validated args and the server-side preview. The model may mark fields uncertain only with an enum reason (`guessedFromHistory`, `guessedFromAttachment`, `ambiguousMatch`, `missingInSource`, `inferredDate`, `convertedCurrency`, `other`) and optional alternative values. Only a clarification card's question and option labels are model text, capped and rendered as plain text.
- **Acting turns show no prose: stream live, retract on the first card.** One rule, in one module (`services/chat/prompt/text-policy.ts`) that both runners feed:
  - assistant text streams live as `text.delta` events;
  - the moment a run creates its first proposal or clarification, the policy emits `text.retracted { partIds }` for every text part the run has produced so far, and from then on drops further text of that run;
  - the stored message never contains text from a run with a card, so a live view (after the retraction) and a reload show the same thing: a server-made header ("3 proposed changes"), the cards and any visuals;
  - the system prompt tells the model to write no text in acting turns, so the retraction is the safety net, not the normal path.

  The CLI runner feeds the same policy from its stdout text events (Claude partial messages, Codex agent messages); the toolkit's propose and clarification tools signal the first card, whichever runner called them.

- **Exact effect = server-computed preview + frozen target set + stale check.** A preview resolver per policy computes what the call will do: before/after for updates, the full row plus related counts for deletes, and count + sample rows for bulk and merge.
  - The only filter-based bulk tool is `bulk_delete_transactions` (`bulk_update_transactions` is id-only; its preview loads the given ids). Its resolver resolves the exact target ids (`resolveBulkTargetIds`) after `validateArgs` accepted the args, and stores them (with their hash) in the snapshot. A bulk delete preview also expands transfer twins (the second leg the delete removes, possibly on another account), so the count, the sample rows and the typed phrase cover every row that goes.
  - At approval, `validateWithRefs` runs on the original filter args first (so `filters: {}` is refused here exactly as the MCP handler refuses it), the filter is re-resolved and compared with the frozen set (a difference makes the card stale), and only then are the args **rewritten to the frozen explicit `transactionIds`** for the handler, so its own filter re-run cannot pick up a row committed after the user confirmed.
  - A different target set, a changed `updatedAt`, a changed base currency or a changed parent makes the card **stale**: it shows what moved and needs a refresh and a new confirmation.
  - Abolished alternative: a dry run of the real handler inside a rolled-back transaction. Handlers have effects outside the database (Redis, BullMQ jobs, PostHog, SSE, outbound fetches), so a rollback does not make them safe to run speculatively.
- **Dependencies through placeholders.** A dependent call uses `"$proposal:<id>"` wherever it needs the id of an entity a pending card will create (a new category for `create_transaction.categoryId`, a new tag in `tagIds`, a new account for `accountId`). The model-facing schema accepts a ref in every uuid position, so neither the AI SDK nor the bridge's MCP layer rejects the call. The proposal service finds the refs (deep scan), records `dependsOn`, substitutes a placeholder UUID and runs the real schema and `validateArgs`.
  - Approving a card applies its pending parents first, in topological order, all or nothing (see "Approval transaction"), substituting each ref with the parent's result id (policy `resultIdPath`, default `id`) and running the real schema and `validateArgs` again on the substituted args.
  - A policy marked `standalone` (a tool that queues work or commits on its own, such as `change_base_currency` or `delete_import_batch`) cannot be part of a chain.
  - Rejecting a parent blocks its dependents.
- **Approval is one database transaction, bound to the revision the user saw** (defined once, under "Approval transaction"). The chain's rows are locked `FOR UPDATE` inside the same transaction that runs the handlers and writes the `applied` statuses, so a second approver waits on the lock and then sees `applied`; a crash rolls everything back and leaves the cards `pending`. Standalone tools, whose effects escape the transaction, pass the same revision, confirmation, validator and stale checks and then use a committed `applying` claim instead; they are never re-run automatically. Every card carries a `revision` that each edit and refresh increments; approve sends the revisions it showed (the card's and its parents'), and a mismatch answers 409 with the current card.
- **Danger and confirmation derive from the existing lists.** `delete_*`, `DESTRUCTIVE_TOOLS`, `CONDITIONAL_DELETE_TOOLS` (on their delete path, e.g. `ignore_payee_name` with `force`), `bulk_*`, `merge_*` and a hand-kept `HIGH_IMPACT_TOOLS` list (`change_base_currency`, `delete_import_batch`, `unlink_account_from_bank_connection`, `remove_duplicate_transactions`, `merge_duplicate_transactions`) are red.
  - A red card affecting one record needs a second confirmation (`ResponsiveAlertDialog`, destructive variant, as the frontend rules require).
  - A red card affecting more than one record, and every high-impact card, needs the affected count typed. A number reads the same in every locale, so `uk` needs no translated phrase.
  - **Egress cards** (policy `egress`: the tool makes the server send a request to a host the arguments name, at apply time or later, e.g. `set_currency_rate_source` with an `http` source, whose `urlTemplate` the sync fetches again and again) are amber, show the full URL and host, and need a second confirmation that repeats the host. They are never "safe".
- **Uncertainty rule in the prompt, structure in the tools.** Material ambiguity (which account, which of two transactions, which amount or date) → `ask_clarification` (options + optional free text). The run stops on that call on both runners: the toolkit records the clarification and marks the run `awaitingClarification`; from then on it answers every further tool call of that run (reads, proposals, a second clarification) with a tool error ("waiting for the user's answer, end your turn") and creates nothing. The AI SDK runner also stops through `stopWhen: hasToolCall('ask_clarification')`; the CLI runner, on the toolkit's signal, lets the clarification's tool result reach the CLI and then ends the process (Claude: close stdin and abort; Codex: abort) after the next stdout event or 2 s, whichever comes first. The run finishes `complete` with the clarification part, and any text it wrote is retracted by the text policy. Defaultable details (category, payee spelling, time of day) → a best guess with `_chat.uncertain`.
- **Visuals through display tools.** `render_chart`, `render_table` and `render_kpis` take a validated spec (Technical Details). The model calls them between text parts, so answers interleave naturally in both paths. Text is plain text with a tiny Markdown subset (bold, italic, inline code, lists, line breaks) parsed into VNodes, never `v-html`. Links and images are not rendered, which closes the classic exfiltration channel of Markdown images.
- **Tool context size: a core set plus discovery.** The full tool list is about 70k tokens, too much to send on every step of every message.
  - The API-key path sends `CHAT_CORE_TOOLS` (about 35 tools under a 60 KB schema budget, unit-tested) plus `find_capabilities` (search over the catalog's names and descriptions; it returns names, descriptions and JSON schemas).
  - `prepareStep` adds every tool the model discovered to `activeTools`, so the provider still sees and enforces each tool's (ref-tolerant) schema.
  - The bridge exposes the same core set natively plus `find_capabilities` and a `use_capability({ name, args, meta })` dispatcher for the long tail. MCP tool lists are static per session and list-change support differs between CLIs, so the dispatcher is the common ground. The bridge is a low-level MCP `Server` with its own `tools/list` and `tools/call` handlers (not `McpServer.registerTool`), so it can advertise the same JSON Schemas as the AI SDK path and route every call through the toolkit's own validation.
- **Transport: SSE over `fetch` per run, with a Redis Stream as the replayable log.** `POST …/messages` answers 202 with the run id. The run executes detached from the request. `GET /chat/runs/:runId/events` streams events with `id:` = Redis Stream id, so `fetch-event-source` resumes with `Last-Event-ID` after a drop. A reload replays the stream from the start while the run is live, and reads the finished message from the database afterwards.
  - **Tailing never runs on the shared Redis client.** `XREAD BLOCK` holds a connection, and the shared client serves the base-currency lock, rate limits and caches. Each process has one tail hub with its own connection (`redisClient.duplicate()`) that multiplexes every open SSE stream into one `XREAD BLOCK … STREAMS k1 k2 …` loop (block 5 s, restarted when the key set changes) and fans results out to the subscribers; a subscriber leaves on disconnect or `run.finished`.
  - Not the app SSE channel: it is a per-user broadcast without replay, and token deltas would fan out to every tab. It only gets a small `chat_thread_updated` event so other tabs refresh their lists.
  - Not `@ai-sdk/vue` `useChat`: cards are server entities with their own lifecycle, and the CLI path produces no AI SDK UI stream.
- **Runs execute in the API process** that accepted the message: CLI runs need the in-process limiter and the loopback bridge anyway.
  - Cancel sets a Redis flag that the runner checks at every step and tool call, besides the local `AbortController`, so a cancel that lands on another replica still stops the run.
  - **Run lease:** a live run refreshes `chat:run:<id>:lease` (TTL 60 s) every 15 s. A sweep at boot and every 2 minutes (a `createScheduledSync` cron) marks every `streaming` message whose lease is gone as `interrupted`, writes `run.finished { status: 'interrupted' }` to its stream and sets the stream's expiry, releases its run counters and revokes its bridge token. A restart mid-run is therefore recovered within about two minutes, whatever the run's age, and reconnecting clients see the end of the stream.
  - Cards created before a cancel or an interruption stay pending.
- **CLI bridge** (Phase 2): see "Chat bridge token" and "CLI chat mode" under Technical Details. In short:
  - a separate **loopback-only listener** (`127.0.0.1`, ephemeral port, plain HTTP, started on first use, self-hosted only) serves a chat-mode MCP server. The public `/mcp` refuses chat tokens, and the listener refuses OAuth tokens;
  - the token is `mmchat_…`, its hash lives in Redis with a TTL that covers the slot wait and the run, it is revoked in the runner's `finally`, scoped to one user and one run with scopes `finance:read chat:propose`, and handed to the CLI only through its environment;
  - Claude runs with `--tools ""`, `--strict-mcp-config` and `--mcp-config` pointing at a 0600 file in the run dir. Codex runs with `--ignore-user-config` and `-c mcp_servers.moneymatter.*`. Each keeps its fail-closed guard, now allowing only `mcp__moneymatter__*` calls (Claude) or `mcp_tool_call` items for server `moneymatter` (Codex);
  - **CLI chat runs take only a global CLI slot.** With parallel runs per connection (prerequisite, see Development Approach), a chat run, like a feature run, waits only for one of the `AI_CLI_MAX_CONCURRENT_RUNS` instance-wide slots. It waits up to 2 minutes (`maxWaitMs`, with a "waiting for the CLI" notice); past that, `CliSlotBusyError` ends the run as `failed` with `chat.cliBusy` ("All CLI slots on this instance are busy; try again in a minute"). Several chats and feature runs on one connection run side by side, so there is no per-connection claim and no per-connection refusal. The CLI chat run keeps the chat run ceiling of 10 minutes, the same as the API path: the shorter 5-minute cap existed only so a chat would not block the connection's other AI features behind a per-connection gate, which no longer exists. Instance-wide slot use stays bounded by the global cap and the 3-runs-per-user limit;
  - the per-message limits are the same constants on both paths and are enforced by the toolkit, which both runners share: 60 tool calls and 100 proposals per message. Model turns are bounded separately: `--max-turns 25` for Claude; Codex `exec` runs one turn with internal tool calls, so it is bounded by the tool-call cap and the wall time. A 40-card statement import therefore works the same on every provider.
- **Sandbox: QuickJS compiled to WebAssembly (`quickjs-emscripten`, release-sync variant) inside a `worker_thread`.** Reasoning:
  - Node's `vm` shares the host's realm machinery and is escapable by design ("not a security mechanism", Node docs). A worker plus `vm` hardening inherits that.
  - `isolated-vm` is real V8 isolation, but it is a native addon: a node-gyp build on the Alpine image, `--no-node-snapshot` on Node 20+, maintenance mode, and a heavy ask for an upstream PR.
  - A Deno/Bun subprocess adds a binary to both images.
  - QuickJS-wasm runs a separate interpreter in WebAssembly linear memory. A bug in QuickJS corrupts only the guest's memory; the host is protected by the wasm sandbox. Nothing is exposed except the functions the host defines (none besides input and output), so there is no network, filesystem, timers, `require` or `process`. It has hard memory and stack limits and an interrupt handler for CPU time, it is pure wasm (works on Alpine, macOS and the hosted image alike), and it is MIT-licensed.
  - The worker adds a second wall (`resourceLimits`, hard `terminate()` at the wall-clock limit) so a host-side hang cannot block the event loop.
  - It is slow (no JIT), which is fine for a few thousand rows.
- **Sandbox input comes from tools, never from the model.** `run_analysis({ code, inputs })`: each input names an earlier tool call of the same run (`fromCall`) or a catalog **read** tool with args (and optional pagination for policy-marked list tools, up to 5,000 rows). The server runs or reuses those reads with the read-only `extra` and passes their JSON. The model cannot inject fabricated data as "input", and the card details show exactly which reads fed a number.
- **Attachments live in the database as prepared content, not as files.**
  - Text (PDF/CSV/TXT through `prepareStatementContent`) is stored capped at 200,000 characters. Images are stored as bytes (≤ `STATEMENT_IMAGE_MAX_BYTES`), because a later turn may re-read them.
  - Raw PDFs and CSVs are not kept. Attachment storage (S3/disk) is not used, so the orphan sweep and the attachment quota are unaffected, and self-hosted instances need no bucket.
  - A later turn sees an attachment as a reference plus a short excerpt and re-reads it with the chat-native `read_attachment`.
- **History is excluded from backups and deleted by wipe and restore.** Threads are a short-lived, self-expiring conversation log full of untrusted copies of documents. Restored proposals would point at the ids of the data that existed before the restore and could be approved against different data. `destroyUserOwnedData` gets an explicit chat step, because it only walks backup-registered tables.
- **The applied-changes record is the card itself.** An applied card keeps its `executedArgs`, `chainId`, `result` refs and `appliedAt`, and "Applied changes" in Settings → AI lists applied cards. It is deleted with its thread (owner's answer 3), so no separate audit table exists.
- **Search uses Postgres full text with the `simple` configuration:** a generated `tsvector` column on messages with a GIN index, plus `ILIKE` on titles. It needs no extension, so self-hosted databases work unchanged. `simple` does no stemming, which treats `en` and `uk` the same way.
- **No included server model, with an extension point (owner's answer 1).** `SERVER_MODELS` and `PLUS_SERVER_MODELS` become `Partial<Record<AI_FEATURE, …>>` and have no `chat` entry, so `getServerModel` returns null for chat and chat needs one of the user's own connections. Adding an operator model later is one entry in those maps: the ladder then offers it to users with `FEATURES.operator_ai`, exactly as for the other features, with no chat code changed. A JSDoc on `SERVER_MODELS` and a docs paragraph name this, and a unit test with a temporary entry proves the path. No plan gating is added.
- **Who may chat:**
  - demo users cannot create threads, attach, send messages or comments, edit or approve cards (`blockDemoUsers`): no own model, throwaway data;
  - read-only (lapsed plan) users may use chat for everything that writes no financial data: create, rename, pin and delete threads, attach files, send messages and comments, answer clarifications (they travel in the message body), cancel runs, refresh and reject cards, change retention. Only approve, approve-all and card edits stay blocked (402), as MCP's `requireScope` would block a write;
  - the mechanism is extended rather than bent: `isReadOnlyAllowed` gets a `READ_ONLY_ROUTE_PATTERNS` list of `{ method, pattern }` rules (the existing `NOTIFICATION_READ` regex moves into it), and the chat rules live there, so `:id` routes match. A unit test pins every chat route's classification;
  - CLI connections stay limited to self-hosted instance admins (`getCliAiAccess`).
- **Base currency:**
  - the approve route carries `checkBaseCurrencyLock`, and the handler checks it again;
  - pending cards do not block a base-currency change: a forgotten chat must not hold the settings hostage;
  - a card whose snapshot base currency differs from the current one is stale.
- **Retention setting** lives in user settings as `ai.chat.retentionDays` (`7 | 30 | 90 | 365 | null`, default 30 at read time). It is written only by `PUT /chat/settings`, which recomputes every thread's `expiresAt` in the same transaction. `ai.chat` joins `SERVICE_OWNED_SETTING_PATHS`, so `PUT` and `PATCH /user/settings` (and with them `update_user_settings`) drop it: a stale cached settings PUT can never write an old retention back without the recompute.

### Data model (one migration `20261018010000-create-chat.ts`)

### Approval transaction (the one definition)

- **Checks shared by both paths, in this order:** (a) every chain row is `pending` and carries the revision the request sent (card and parents); an `applied` chain answers 200 with the applied card (idempotent), anything else 409 with the current card; (b) the confirmation payload matches the strictest requirement of the chain (`confirm` for single red and egress cards, the exact affected count for typed ones), else 422; (c) `validateWithRefs` on every card's original args (refs to parents of the same chain replaced by placeholders, the original filter selection kept, before any bulk-id rewrite); (d) the snapshots recomputed and compared, stale → 409 with the diff (a refresh recomputes the preview and snapshot, returns the card to `pending` and increments `revision`).
- **Post-rollback status writes** (`stale`, `failed`) run in a short second transaction conditional on `status = 'pending' AND revision = <the revision the failed attempt checked>`. When that no longer matches (another tab edited or refreshed the card meanwhile), nothing is written and the response carries the current card, so an obsolete request can never mark a newer revision.
- **Normal tools (everything not `standalone`):** one transaction T, inside `runWithBalanceRevalueBatch`:
  1. `SELECT … FOR UPDATE` on every row of the chain, ordered by id, inside T;
  2. checks (a)–(d); a failure rolls back T and answers as above;
  3. for each card in topological order: substitute its refs with the real ids returned by its parents' handlers, which already ran earlier in this loop inside T, rewrite `bulk_delete_transactions` filter args to the frozen ids, run the real schema and `validateArgs` on the substituted args, `entry.invoke` with the user's full-scope `extra`; the services' `withTransaction` joins T through CLS;
  4. write `applied`, `executedArgs`, `result`, `chainId`, `appliedAt` on every row, inside T; commit.

  A concurrent approver blocks at step 1 and then sees `applied`. A crash before the commit rolls back every write and every status and leaves the cards `pending`; a handler error rolls back the same way and is then recorded as `failed` by a post-rollback write. Double apply is impossible because statuses and data commit together.

- **Standalone tools** (`change_base_currency`, `delete_import_batch`, …; never chained): in one short transaction, `SELECT … FOR UPDATE` on the row, checks (a)–(d), then `UPDATE … SET status = 'applying' WHERE id = :id AND status = 'pending' AND revision = :revision`; commit (the claim). A failed check writes nothing but the post-rollback status. The handler then runs with the claimed args, and a second transaction writes `applied` or `failed`. A crash in between leaves `applying`; the hourly chat cron (Task 14) turns an `applying` row older than 10 minutes into `unknown` ("check whether this change happened"), and nothing ever re-runs it.

### Card schema (shared `ChatProposalCard`, what the API returns)

  title: { key: string; params: Record<string, string | number> };

  safe: boolean; // eligible for "Approve all safe"

  sources: ChatSource[]; // tool calls (name + compact args), attachments, page context, analyses

  stale?: { reasonKey: string; before?: unknown; after?: unknown };

- The `_chat` meta field on every proposed call (stripped before validation):
  - `uncertain?: { field, reason, alternatives? }[]`;
  - `replaces?: proposalId`: a comment answered with a new card supersedes the old one;
  - `sourceCallIds?: string[]`: narrows the sources; the default is every read of the run before the call.
- **Editable fields:** top-level primitives, enums, dates and the id fields the policy maps to an entity picker (`accountId`, `categoryId`, `payeeId`, `tagIds`, `currencyCode`, …). Nested structures (splits, filter objects, budget-plan layouts) are read-only in v1 and changed through a comment. An edit re-validates with the tool's schema and `validateArgs` (refs allowed as on proposal), recomputes danger, egress, preview and snapshot, increments `revision`, and resets any confirmation.

### Model-facing schemas (`services/chat/toolkit/model-schema.ts`)

- Built once per catalog entry: the input shape → JSON Schema with the same conversion the MCP SDK uses for `tools/list`, slimmed by `slimToolListSchema`; then every `format: uuid` position (top level, array items, nested objects, unions) is widened to `anyOf: [{ type: string, format: uuid }, { type: string, pattern: "^\\$proposal:[0-9a-f-]{36}$" }]`; write tools get the optional `_chat` property. Tools with no input get `{ type: object, properties: {} }`.
- The AI SDK path passes it as `jsonSchema(schema, { validate })`. Verified in the installed `ai` 6.0.300: `safeValidateTypes` (`@ai-sdk/provider-utils`) returns `result.value` from a custom `validate`, and `doParseToolCall` passes that value to the tool as its `input`, so whatever `validate` returns replaces the input. The hook therefore **only checks**: it calls `validateWithRefs` (refs to placeholders on a copy, then the real zod schema and `validateArgs` on that copy), and returns `{ success: true, value: input }` with the original input unchanged (`$proposal:` refs and `_chat` intact), or `{ success: false, error }`, which the model sees as an input error and repairs. `execute` (the toolkit's propose path) is the single place that strips `_chat`, records refs and substitutes placeholders. The bridge advertises the same JSON Schema in its own `tools/list` (Task 19).
- Both paths run the real schema and `validateArgs` again in `execute`; the widened schema is never used to accept data on its own.

### Approve-all and safe cards

- `isSafeForApproveAll(card)` is true only when the card is `pending` and fresh (snapshot rechecked), `danger: none`, `confirmation: none`, not `egress`, not `standalone`, not `settings` kind, `canApply.ok`, has no uncertain field, and every pending parent is safe too.
- `POST /messages/:id/approve-all` applies every safe pending card of the message, each chain in its own approval transaction, sends each card's revision as returned by the list the user saw, and returns per-card results. Unsafe cards stay pending and are named in the response. The button shows the count of safe cards and is hidden when there are none.

### Tool policies (`services/chat/policies/`)

- **Rules first, then explicit entries.** `create_*` → create; `update_*` / `set_*` → update (before/after through an entity loader); `delete_*` → delete (red); `bulk_*` → bulk (red when deleting, typed when count > 1); `merge_*` → merge (red, typed); `link_*` / `unlink_*` / `assign_*` / `remove_*` → link; settings tools → settings; anything else → `action`. The entity comes from the name (`create_budget_plan_line` → `budgetPlanLine`) unless overridden.
- **Policy fields:** `kind`, `entity`, `danger`, `previewResolver`, `resultIdPath`, `standalone`, `egress` (the tool makes the server send a request to a host its arguments name, at apply time or later, e.g. `set_currency_rate_source` with an `http` source; a function of the args, so a CoinGecko source is not egress while an HTTP one is; the card shows the URL and host, needs a confirm that repeats the host, and is never safe; Task 8 greps the services behind every write tool for `createGuardedFetch`, `fetch(` and stored URL fields to complete the hand-kept `EGRESS_TOOLS` list), `pagination` (read tools that `run_analysis` may page: `search_transactions`, `get_payees`, …), `entityFields` (id field → picker).
- **`CHAT_EXCLUDED_TOOLS`** (each with a reason, drift-tested):
  - `create_attachment_upload_url`: returns an upload credential URL, and the chat cannot upload bytes;
  - `test_currency_rate_source`: a probe whose only effect is an outbound request; the rate-source card shows the URL instead.
- **`CHAT_ARGS_ONLY_TOOLS`:** write tools whose card shows the validated args without a computed preview. It is explicit, so a new tool cannot land there silently. Red tools may not be in it.
- **Preview resolvers:**
  - entity loaders (row + related counts where a count service exists: `get_account` `transactionCount`, `get_category_transaction_count`, tag transaction counts) for transaction, account, category, tag, payee, budget, budgetPlan and its parts, subscription, loan, vehicle, portfolio, holding, investment transaction, transaction group, automation, template, venture platform/deal/event, custom currency, user currency;
  - explicit resolvers for `bulk_delete_transactions` (ids or filters, filters through `resolveBulkTargetIds` after `validateArgs`; count + 10 rows; also lists the transfer twins it removes and their accounts), `bulk_update_transactions` (id-only: loads the given ids; count + 10 rows + before/after of the changed fields), `bulk_delete_payees`, `merge_payees` (sources, transaction and alias counts), `remove_duplicate_transactions`, `merge_duplicate_transactions`, `delete_import_batch` (batch effects), `change_base_currency` (accounts and rows to revalue), `delete_exchange_rates`, `apply_transaction_automation` (matched rows through the preview service), `apply_payee_tags_to_transactions`.
- **The chat capability drift suite** (`services/chat/policies/chat-capabilities-drift.unit.ts`), over `getToolCatalog()`:
  1. every tool is a capability or in `CHAT_EXCLUDED_TOOLS`;
  2. every write capability resolves to a policy;
  3. every `delete_*`, `DESTRUCTIVE_TOOLS`, `CONDITIONAL_DELETE_TOOLS`, `bulk_*`, `merge_*` and `HIGH_IMPACT_TOOLS` tool is red and has a non-args-only resolver;
  4. every explicit entry and list item names an existing tool;
  5. every `CHAT_CORE_TOOLS` entry exists and the core schemas stay under 60 KB;
  6. every top-level field of every write capability has a key in `CHAT_FIELD_LABEL_KEYS` (shared const), whose keys a frontend unit test checks in the `en` and `uk` chunks;
  7. every title key (kind × entity) exists;
  8. every `EGRESS_TOOLS` entry exists and has an egress function, and its card comes out amber, with a confirm and `safe: false`, for an args fixture that names a host;
  9. no red, egress, standalone or settings card is ever `safe` (property check over a fixture card per tool).

  A new MCP tool therefore becomes a chat capability by itself, and the suite fails until it has the right card type.

### Chat bridge token (Phase 2)

- **Mint:** `mintChatBridgeToken({ userId, threadId, runId })` in the CLI runner, after `assertCliAiAllowed`. The token is `mmchat_` + 32 random bytes base64url. Redis `chat:bridge-token:<hashToken(token)>` → `{ userId, threadId, runId, provider, expiresAt }`, with TTL = slot wait + run timeout + margin (2 + 10 + 1 = 13 min) at mint; when the slot is acquired, the runner resets the TTL to run timeout + margin (11 min) from that moment, so neither a long slot wait nor a full-length run outlives its token, and an abandoned token still dies within 13 minutes. The raw token exists only in the runner's memory and the CLI's environment (`MM_CHAT_TOKEN`). It is never logged, never in argv and never in a prompt.
- **Scope:**
  - `McpAuthInfo` built by `buildMcpAuthInfo` (extracted from `verifyAccessToken` in Task 1), so entitlements resolve the same way;
  - `clientId: 'moneymatter-chat-bridge'`, scopes `['finance:read', 'chat:propose']` (no `finance:write`, so even a real write handler would refuse), `extra.chat = { threadId, runId }`;
  - the chat-mode server registers propose wrappers, never the write handlers;
  - the run must still be `streaming` in the database, checked on every request.
- **Expiry and revocation:** the TTL; `revokeChatBridgeToken` in the runner's `finally` (success, error, cancel, timeout); revoke-by-run on thread delete and user wipe; the run-lease sweep revokes the token of an interrupted run. The bridge enforces nothing of its own beyond the token: every call goes through the run's toolkit, which applies the same per-message limits as the API path (60 tool calls, 100 proposals, 10 third-party reads, 5 analyses).
- **Relation to OAuth MCP tokens:**
  - a different issuer and store (Redis, not `ba_oauth_access_token`);
  - no consent or refresh: the server mints it for the user's own session, for one run;
  - not listed under Connected apps;
  - `verifyMcpToken` rejects the `mmchat_` prefix up front on the public `/mcp`, and the loopback listener accepts nothing else;
  - `hashToken` moves to `common/lib/hash-token.ts` exactly as `feat/apple-pay-ingest` moves it (same name, same output, a pinning unit test), so whichever branch lands second resolves to the same file.
- **Sessions:** `transport-manager` sessions record `{ userId, kind: 'oauth' | 'chatBridge', runId? }`, and a bridge request must match both the user and the run. Bridge sessions close at run end.
- **Listener:**
  - `services/chat/bridge/bridge-listener.ts`: a minimal Express app on `127.0.0.1:0` with `express.json({ limit: '1mb' })` and the MCP request handlers, started lazily, only when `isSelfHost()`, closed on shutdown;
  - the handlers are extracted from `routes/mcp.route.ts` into `services/mcp/http-handlers.ts` (`createMcpHandlers({ authenticate, createServer })`) and shared by both; the bridge's `createServer` builds the low-level chat-mode `Server` (own `tools/list` and `tools/call`, see "Model-facing schemas");
  - the CLI dials `http://127.0.0.1:<port>/mcp`: no TLS, no Cloudflare Access in the way, no public exposure.

### Sandbox (Phase 3, `services/chat/sandbox/`)

- `runSandboxedAnalysis({ code, inputs })`:
  - a pooled `worker_thread` (pool size 2, `resourceLimits.maxOldGenerationSizeMb: 128`) loads `quickjs-emscripten` (exact version pinned);
  - each call gets a fresh runtime with `setMemoryLimit(64 MB)`, `setMaxStackSize(512 KB)` and an interrupt deadline of 2 s of CPU; the worker is terminated at 5 s wall clock;
  - code ≤ 20 KB, total input ≤ 8 MB JSON, output ≤ 256 KB.
- **Guest environment:**
  - `input` (deep-frozen, parsed inside the guest from a JSON string);
  - a pure helper library evaluated first: `sum`, `mean`, `median`, `percentile`, `groupBy`, `sortBy`, `movingAverage`, `byMonth`, `minor.sum(values, decimals)` (integer minor-unit arithmetic, matching the repo's report engines);
  - no `Date.now`-dependent helpers; no host functions.
- **Output contract:** `return { values?, tables?, charts?, kpis? }`, validated with the visual spec schemas. Errors (syntax, runtime, limit) go back to the model with their kind, so it can fix the code.
- The analysis part stores the code, the input sources and the output. "Details" shows the code read-only.

### Prompt (`services/chat/prompt/`, `CHAT_PROMPT_VERSION` stored per message)

- **System prompt sections:**
  1. role and the two modes, with the "never claim a change is done; cards are the only way to change data" rule;
  2. the card rules: one call per change, `$proposal:` refs, `_chat.uncertain` and its enum, when to use `ask_clarification`;
  3. answering rules: numbers only from tool or analysis results, visuals through `render_*`, short plain text in the user's UI language;
  4. `FINANCIAL_DATA_GUIDE_CONTENT` (reused from the MCP prompt);
  5. date, time zone, locale, base currency;
  6. the untrusted-data rule;
  7. the page context, if any.
- **History builder:**
  - the newest turns first, within `min(0.6 × model context, 120k)` tokens (`estimateTokenCount`);
  - older tool results are replaced by their summary ("call again if needed");
  - card states are rendered as one line each (`proposal p_1 create_transaction: applied | rejected (reason) | pending`);
  - attachments of earlier turns as reference + excerpt.
- **Untrusted wrapping:** each attachment's text and each tool result is wrapped in `<<<UNTRUSTED kind=… nonce=<128-bit hex>>>> … <<<END nonce>>>`, with the nonce stripped from the content first, so a document cannot close the block. Page-context names go inside such a block too.
- **Prompt-injection defence, layered:**
  1. no write without a click: proposals only; the executor runs only on the approve endpoint, under the user's session;
  2. exact, server-made cards (preview, frozen target set, stale check); no model prose on cards;
  3. red cards with a second or typed confirmation;
  4. untrusted wrapping plus the system rule; instructions found in data are ignored, and the model may say the document contained some;
  5. egress kept small: read tools that call third parties (`search_coingecko_coins`, `search_securities`) are capped at 10 calls per message; write tools with egress get an amber card with the URL and host, a confirm that repeats the host, and are never applied by "Approve all safe"; plain-text rendering shows no links or images;
  6. no secrets in context: credential-returning tools are excluded, and tokens never go into prompts;
  7. provenance in "details" for every card;
  8. the limits below;
  9. e2e fixtures that try it.

- card-mapping set / delete → update card with an account picker / red delete card;
- retry a parked payment → `action` card whose preview is the parked payment summary (amount, merchant, card, target account), standalone;
- dismiss → red when it deletes the request row, else `action`;
- list tools → reads (unconfirmed card payments become a good chat question).
